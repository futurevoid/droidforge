# Incident 2026-09-25 - ColorOS Settings UI broken

Device: realme Neo 8 (RMX8899), China ROM, Android 16, no root.

## Root cause (confirmed by the owner)

**Developer options > "Disable permission monitoring"** (renamed "Disable system optimization" on newer builds;
Chinese 禁止权限监控) was switched **on**. Claude recommended it, because ColorOS refused
`pm grant ... CHANGE_CONFIGURATION` (MoreLocale) and the locale-setter DEX without it.

The switch turns off ColorOS's own system layer. The effect matched everything the owner saw:

- Settings pages came up as stock-Android versions (e.g. an AOSP "Display" page) instead of ColorOS ones;
  toggles rendered "off" while their state said "On"; washed-out colours.
- App info > Permissions: the ColorOS PermissionController trampoline
  (`com.oplusos.permissioncontroller...ManagePermissionsActivityTrampoline`) chose the stock page, pale and
  light while the phone was in dark mode.
- ColorOS's colour value in the live config was `mMaterialColor= 0` while the saved setting
  `material_color_value` was `17179869184`.

**Settings > Reset all settings fixed it**: that reset puts developer options back to their defaults, which turned
the switch off. The owner then confirmed the switch was the cause.

## What was wrongly suspected first

The diagnosis went through the legacy tool's changes one by one. That was the wrong order:

| Suspect | Result |
|---|---|
| Per-app locale overrides on every package | removed -> still broken |
| Package state (disabled/removed/suspended/neutered) | back to first snapshot -> still broken |
| Font scale, dark-mode lightness values | healthy -> not the cause |
| Device language / DEX `updatePersistentConfiguration` | blamed for a while; not the cause |
| **"Disable permission monitoring" switch** | **the cause** (an earlier message in the session wrongly recorded it as "not the cause") |

Lesson for diagnosis: first list **every** change made to the phone in the session, *including advice the user
followed by hand*, and test the most global one first.

## Rules that follow

Primary (the actual cause):

1. droidforge **never** tells the user to turn on "Disable permission monitoring", "Disable system optimization",
   or any other developer-option switch, never writes the setting behind it, and has no feature that needs it.
   If ColorOS refuses a command without that switch, droidforge reports the refusal and drops the feature.
2. The switch's state is a **health probe**. If it is on (whoever turned it on), droidforge shows the breakage alert
   and tells the user to turn it off (Developer options, bottom of the list), then reboot.

Kept as defence in depth (owner's standing order: never break anything, never change what doesn't need changing):

3. No writes to the persisted global configuration, `system_locales` or `persist.sys.locale`; no
   `CHANGE_CONFIGURATION` grants (these only worked *because* of the switch).
4. No display/UI settings at all; per-app locales only on user-picked non-system apps; no bulk passes.
5. Command allowlist, blast-radius diff, health gate, batches of 5, recovery script, breakage alert with Fix it.
